# Чек-лист приёмки на живом Swarm

Проходится один раз перед тегами `v1.0.0` / `v2.0.0`. Всё, что не удалось
проверить в CI и на тестах: реальный кластер, реальные ноды, реальный Docker.

**Где проверять:** сначала на тестовом кластере (2–3 ноды), и только потом
трогать боевой. Пункты, помеченные ⚠️, изменяют состояние кластера.

---

## 1. Установка с нуля

- [ ] На чистом Swarm выполнена процедура из README:
      создание секретов `agent_token` и `encryption_key`, `docker stack deploy`.
- [ ] `docker service ls` — `dsms_panel` 1/1, `dsms_agent` N/N (по числу нод).
- [ ] Хелсчеки зелёные: `docker ps --filter name=dsms --format '{{.Names}} {{.Status}}'`
      показывает `(healthy)` у обоих.
- [ ] Reverse proxy настроен по README, панель открывается по HTTPS.
- [ ] `curl https://<домен>/api/v1/healthz` возвращает `status`, `version`, `commit`, `schema`.
- [ ] Первый вход: экран первичной настройки, создание admin, вход работает.

## 2. Мониторинг (FR-01, FR-02)

- [ ] Дашборд показывает все ноды, метрики обновляются без перезагрузки страницы.
- [ ] Графики CPU/RAM/диск/сеть живые; окно 15 минут заполняется.
- [ ] Страница ноды: диски, сеть, список контейнеров с топом по CPU/RAM.
- [ ] Задержка от события до отображения ≤ 5 секунд (NFR-3).
- [ ] После `docker service update --force dsms_panel` (рестарт панели)
      15-минутный график **восстанавливается**, а не начинается с нуля.

## 3. Управление нодами (FR-03)

- [ ] ⚠️ Drain worker-ноды: задачи переехали, статус в UI обновился.
- [ ] ⚠️ Возврат ноды в active.
- [ ] Редактирование labels ноды сохраняется.
- [ ] Join-токены отображаются; ⚠️ добавление новой ноды по инструкции из UI
      работает, агент на ней появляется сам (mode: global).
- [ ] Панель **запрещает** demote/drain последнего manager'а.

## 4. Сервисы и стеки (FR-04, FR-08)

- [ ] Список сервисов: статус реплик совпадает с `docker service ls`.
- [ ] Страница сервиса открывается **и для сервиса без `deploy.placement`**
      (раньше это давало 500).
- [ ] ⚠️ Scale вверх/вниз применяется.
- [ ] ⚠️ Stop → сервис в 0 реплик; Start возвращает **прежнее** число реплик.
- [ ] ⚠️ Redeploy перезапускает задачи на том же образе.
- [ ] ⚠️ Deploy подтягивает свежий образ по тому же тегу.
- [ ] ⚠️ Rollback возвращает предыдущую спецификацию.
- [ ] Порядок обновления берётся из стека: сервис с `order: stop-first`
      не превращается в start-first (проверить `docker service inspect`).

## 5. Деплой стека из файла (FR-14)

Отдельный тестовый стек, **не боевой**.

- [ ] «Проверить» показывает сервисы, сети, секреты и предупреждения.
- [ ] Файл с `build:`/`depends_on:` даёт понятные предупреждения.
- [ ] Ссылка на несуществующую `external`-сеть попадает в «отсутствующие».
- [ ] ⚠️ «Развернуть»: стек поднимается с нуля — сети, секреты, сервисы.
- [ ] **Том проверен по-настоящему:** сервис с БД записал данные →
      `docker service update --force` → данные на месте.
- [ ] Секрет из `environment:` создан и доступен внутри контейнера
      (`docker exec ... cat /run/secrets/<имя>`).
- [ ] Созданная сеть имеет label:
      `docker network inspect <стек>_<сеть> --format '{{.Labels}}'`.
- [ ] Правка файла + «Обновить»: изменённый сервис обновлён, новый создан.
- [ ] ⚠️ С включённым prune исчезнувший из файла сервис удалён;
      **чужие стеки не затронуты** (`docker service ls` до/после).
- [ ] «Скачать YAML» отдаёт тот же файл, что загружали.
- [ ] В журнале действий есть `stack.deploy_file` **без** содержимого
      yaml/env (проверить, что секреты не утекли).

## 6. Логи, события, алерты (FR-05, FR-06, FR-12)

- [ ] Логи сервиса стримятся живьём; переключение на другой сервис работает.
- [ ] Уход со страницы и возврат — логи снова идут (стрим не «залипает»).
- [ ] История логов подгружается при скролле вверх.
- [ ] Лента событий показывает реальные события кластера.
- [ ] Алерт срабатывает: остановить агента на ноде → через ~60с
      появляется `agent_silent`, после возврата — resolved.

## 7. Ресурсы и очистка (FR-09…FR-11)

- [ ] Secrets: создание работает, значение **обратно не показывается**.
- [ ] Configs: содержимое читается.
- [ ] Тома и сети отображаются по нодам.
- [ ] ⚠️ Prune на одной ноде освобождает место, отчёт совпадает с
      `docker system df` до/после.

## 8. Данные и эксплуатация (NFR-9…NFR-11)

- [ ] Settings → «Скачать копию»: файл открывается `sqlite3`,
      в нём есть таблица `stacks` с исходником стека.
- [ ] ⚠️ Обновление образа панели на новую версию: миграции применились
      сами, данные (пользователи, стеки, история) на месте.
- [ ] ⚠️ Попытка запустить **старый** образ на новой БД — панель
      отказывается стартовать с понятным сообщением в логах.
- [ ] Версия в углу интерфейса совпадает с тегом образа.
- [ ] Логи панели — валидный JSON (NFR-8): `docker service logs dsms_panel | head -1 | jq .`

## 9. Безопасность (FR-07)

- [ ] Панель недоступна напрямую по IP:9000 снаружи кластера.
- [ ] 6 неверных попыток входа подряд → 429; попытки с подделанным
      `X-Forwarded-For` **не сбрасывают** счётчик.
- [ ] Запрос с неверным CSRF-токеном отклоняется (403).
- [ ] В журнале действий есть записи по всем опасным операциям.
- [ ] `docker service logs dsms_panel | grep -i -E 'password|token|secret'`
      не показывает значений секретов.

## 10. Ресурсы и релиз

- [ ] Потребление: панель ≤ 256 МБ, агент ≤ 20 МБ RAM
      (`docker stats --no-stream`).
- [ ] Размеры образов: panel ≤ 25 МБ, agent ≤ 15 МБ
      (`docker image ls | grep dsms`).
- [ ] Тег `v1.0.0` / `v2.0.0` поставлен, release-workflow опубликовал
      multi-arch образы в ghcr.io.
- [ ] Образ с ghcr.io запускается на arm64-ноде (если такая есть в кластере).
