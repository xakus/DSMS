# Этап 15. Таблицы без «прыжков», причины прочерков, честная очистка дисков

ТЗ v1.5: разделы 6.4, 3.4.7, 2.3, 4.3, FR-11 (3.11.2, 3.11.5, 3.11.6).
Источник — замечания Мурада с боевого кластера (25.11.2026, скриншот ширины 3800 px).

## Что сделано

**Фронтенд**
- `utils/columns.ts` + `composables/useColumnWidths.ts` — ширины колонок по весам
  под ширину контейнера (ResizeObserver); `styles/tables.css` (класс `.live-table`) —
  строка 68 px, `tabular-nums`. Подключено в четырёх таблицах: сервисы, стеки,
  сервисы стека, задачи сервиса. Все таблицы — `table-layout="fixed"`.
- `utils/usage.ts` — прочерк с подсказкой-причиной, «Ноды» и «Порты» не больше
  двух строк («ещё N»); `utils/replicas.ts` — общая ячейка реплик: жёлтый при
  running > desired, подсказки к числам и к значку обновления.
- `usePolling` — интервал из настройки `metrics.interval_sec` (как у агентов).
- Задачи сервиса: колонка «Образ» (видно, какая задача на какой версии).
- `DiskUsageView` — «освободится» из новых полей агента, подсказки про кэш сборки
  и именованные тома, кнопка «Очистить всё», тексты через i18n.

**Панель**
- `metrics.TaskStats`: `Put(node, tasks, state)` заменяет цифры только при полном
  батче; `Agents()` — состояние агента ноды (ok / silent / outdated / failed).
- `/services`, `/services/{id}`: поле `no_data` (нода + причина).

**Агент**
- `collector`: `tasks_state` в батче, предел ожидания Docker 10 с.
- `dockerops/containers.go`, `stats.go`: cgroup v1 + systemd; нет cgroup —
  цифры через Docker stats API (лимит памяти — из настроек контейнера).
- `dockerops/layers.go`, `df.go`: оценка очистки по дереву слоёв образов, слои в
  кэше сборки — отдельно, счётчики удаляемых объектов, итог полной очистки;
  порядок полной очистки закреплён в `PruneOrder`.

## Критерии и проверка

- [x] Юнит-тесты: `agent` (дерево слоёв, df, cgroup v1, разбор Docker stats),
  `panel` (хранилище метрик задач, причины `no_data`, сбойный батч), `frontend`
  (раскладка ширин, цвет и подсказки реплик) — зелёные.
- [x] `golangci-lint` (panel, agent) и `eslint` — чисто.
- [x] Скриншоты: сервисы на 3800 / 1920 / 1280 / 768 / 360 px, светлая и тёмная
  темы; стеки, страница стека, страница сервиса, диск. Замер в браузере: все
  строки таблиц ровно 68 px, раскладка `fixed`, прокрутки страницы нет.
- [x] Живая проверка на стенде docker-in-docker (Docker 29.10.1):
  - оценка очистки против результата — совпадение байт в байт по каждой кнопке
    и по «Очистить всё» (25,00 и 40,00 МБ) на классическом хранилище образов,
    с кэшем сборки и без него; на containerd-хранилище — «не меньше»
    (15,02 МБ против 15,03 МБ);
  - именованный том с данными очисткой не удалён;
  - цифры сервисов против `docker stats`: обычный путь и запасной (агент без
    `/sys` хоста) — CPU 2,00 ядра против 2 × 100,6 %, RAM совпала;
  - агент без `docker.sock`: цифры держатся, через 90 с — прочерк с причиной `failed`.

## Что узнали (не сломать)

- Образ, собранный на ноде, делит слои с кэшем сборки: `docker image prune`
  удаляет образ, но место освобождает только `docker builder prune`. Запись кэша
  не несёт идентификатор слоя — сопоставляем по размеру (он равен размеру слоя
  байт в байт). Проверено только на классическом хранилище.
- Какой слой нулевого размера какому шагу истории соответствует, Docker API не
  говорит. Дерево слоёв обходится без этого: общая часть двух образов — общее
  начало их последовательностей ненулевых размеров, не длиннее числа общих слоёв.
- Расчёт сверяется с `SharedSize` из `docker system df`; на containerd-хранилище
  (Docker 29 по умолчанию) цифры устроены иначе — там оценка всегда «не меньше».
- На стенде два агента с одним `NODE_ID` (один без `docker.sock`) ломали экран
  диска: панель ходит к агенту по адресу последнего батча. На бою такое
  бывает при незавершённом обновлении сервиса агента — лечится доведением
  обновления до конца.

## Что не входит

- Удаление неиспользуемых именованных томов кнопкой очистки (намеренно: данные).
- Поиск причины лишних задач у global-сервиса на бою — только показ (жёлтый цвет
  и подсказка); действие — «Передеплой» сервиса или повторный `docker stack deploy`.
- Push потребления сервисов по WebSocket вместо опроса.
