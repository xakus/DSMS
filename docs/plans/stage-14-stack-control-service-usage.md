# Этап 14 — Управление стеком целиком и потребление ресурсов сервисов

Требования ТЗ v1.4: FR-08 (3.8.2, 3.8.3, 3.8.6, 3.8.7), FR-04 (3.4.1, 3.4.4, 3.4.7),
3.14.13, раздел 4.3 (`tasks`), NFR-2a.

## Зачем

1. В меню «Стеки» есть удаление, но нет остановки и запуска стека целиком —
   приходится останавливать сервисы по одному.
2. По сервису не видно главного: **на каких нодах он работает и сколько ест**
   (CPU, RAM, сеть). Метрики контейнеров есть только на странице ноды и только
   топ-20 — по сервису их не собрать.
3. Проверка кода стеков против ТЗ нашла дыры (таблица ниже).

## Объём

### 14.1. Stop / Start стека (S-01, S-08, S-11, S-12)

- `POST /stacks/{name}/stop`, `POST /stacks/{name}/start` — правила ТЗ 3.8.3.
- Общие `stopService` / `startService` для сервиса и стека (один код — одно поведение);
  при ошибке Docker запись `service_state` откатывается.
- `GET /stacks`: `stopped` (остановлено панелью), `stoppable` (можно остановить),
  `usage` (сумма потребления).
- UI: кнопки «Остановить» / «Запустить» (неактивны, когда нечего делать),
  статус «остановлен».

### 14.2. Удаление и групповые операции (S-02…S-06)

- Удаление: сервисы → сети → secrets → configs с label стека; тома не трогаем.
- Стек «существует», если есть сервисы, **или** объекты с label, **или** запись в БД.
- Единая сводка `done / skipped / failed` (ТЗ 3.8.6) для stop/start/redeploy/deploy/remove.
- Имя стека — по ТЗ 3.14.13, проверка до сохранения исходника.

### 14.3. Страница стека (S-07)

- `GET /stacks/{name}`: сервисы + `networks`, `volumes`, `secrets`, `configs`
  (из спецификаций сервисов и по label стека).
- `StackDetailView.vue`: сводка, действия, таблица сервисов с потреблением, ресурсы.

### 14.4. Метрики задач (V-04, ТЗ 3.4.7)

- **Агент:** для каждого контейнера с label `com.docker.swarm.task.id` —
  CPU в ядрах, RAM (без неактивного файлового кэша), лимит RAM, сеть rx/tx.
  Сеть: PID контейнера (один `ContainerInspect` на контейнер, кэш) →
  `/host/proc/<pid>/net/dev`. `network_mode: host` — сеть не считаем.
- **Панель:** `metrics.TaskStats` — последнее значение по ноде, срок жизни 90 с.
  `ingest` вырезает `tasks` из снапшота до буфера, БД и WebSocket.
- Старый агент + новая панель → прочерки вместо цифр; новый агент + старая панель →
  поле игнорируется. Порядок обновления не важен.

### 14.5. Сервисы в UI (V-01…V-03, S-09, S-10)

- Таблица сервисов: колонки «Ноды», CPU, RAM, сеть ↓/↑.
- Страница сервиса: сводка, потребление по задачам, полная спецификация, иконки.
- Опрос без мигания спиннера; ошибка опроса — один тост, а не поток.

### 14.6. Исправления по итогам живой проверки (L-01…L-06)

- **L-01:** `serviceNetworks` добавляет псевдоним — короткое имя сервиса — на
  каждую сеть, кроме встроенных `host`/`bridge`/`none` (ТЗ 3.14.5).
- **L-02:** счётчики ноды читаются из `$HOST_PROC/1/net/dev`; в батч идут только
  аплинки (`collector/netifaces.go`, ТЗ раздел 2.3).
- **L-03:** `streams.IsRealFailure` — алерт только если задача Swarm в состоянии
  `failed`/`rejected` (ТЗ 3.12.1).
- **L-04:** «не найдено» при удалении объекта стека — успех, а не сбой.
- **L-05:** значок обновления — только для незавершённых состояний.
- **L-06:** ширины таблиц под 1280 px; редкие действия сервиса на экранах уже
  1440 px уходят в меню «ещё».

## Критерии проверки

- [x] `go build`, `go vet`, `go test`, `golangci-lint` чисты в `panel/` и `agent/`.
- [x] `npm run build`, `npm run lint`, `npm run test` чисты.
- [x] Тесты: stop/start стека (global пропущен, повторный stop, start без stop),
      удаление с сетями/secrets/configs, удаление managed-стека без сервисов,
      плохое имя стека → 400 и ничего не сохранено, `usage` в `/services` и
      `/services/{id}`, срок жизни `TaskStats`, разбор `/proc/<pid>/net/dev`,
      RAM минус `inactive_file`.
- [x] Живая проверка на Swarm (одна нода в docker-in-docker, агент в контейнере
      с `HOST_PROC`/`HOST_SYS`, как в `dsms.yml`): стек из файла → stop → start →
      удаление; у сервиса видны нода, CPU, RAM и сеть под нагрузкой, цифры
      сходятся с `docker stats` (CPU 99.3% против 99.99%, RAM 19.9 против 19.94 МиБ).
- [x] Скриншоты: стеки, страница стека, сервисы, страница сервиса — 360 / 768 / 1280 px,
      светлая и тёмная тема.
- [x] Размеры бинарников в лимитах образов: панель ≤ 25 МБ, агент ≤ 15 МБ.

Не проверено на этом этапе: кластер из нескольких нод (сумма потребления по
нодам покрыта только тестом с двумя нодами-заглушками) и cgroup v1.

## Что не входит

- Остановка global-сервисов (в Swarm нет scale 0 для global; вариант через
  constraint — отдельное решение).
- История потребления сервиса (графики) — данные только «сейчас».
- Сеть по контейнерам на странице ноды.

## Рецепт живой проверки (одноразовый Swarm, основной Docker не трогается)

```bash
# 1. Отдельный Docker в контейнере + Swarm из одной ноды.
#    Версию образа docker:*-dind сверить со списком тегов в реестре.
docker run -d --privileged --name dsms-dind-test -e DOCKER_TLS_CERTDIR= \
  -p 127.0.0.1:19000:9000 docker:<версия>-dind
docker exec dsms-dind-test docker swarm init

# 2. Панель — процессом внутри стенда (фронт собрать заранее: npm run build).
cd panel && CGO_ENABLED=0 go build -o /tmp/panel ./cmd/panel
docker cp /tmp/panel dsms-dind-test:/panel
docker exec -d -e DSMS_DB=/data/dsms.db -e DSMS_AGENT_TOKEN=dev-token \
  -e DSMS_COOKIE_INSECURE=1 -e DSMS_ENCRYPTION_KEY=<64 hex-символа> \
  dsms-dind-test sh -c 'mkdir -p /data; /panel > /var/log/panel.log 2>&1'

# 3. Агент — В КОНТЕЙНЕРЕ, с теми же монтированиями, что в dsms.yml:
#    только так проверяются HOST_PROC/HOST_SYS и сетевые пространства.
#    Адрес панели — шлюз docker0 ВНУТРИ стенда (ip addr show docker0).
cd agent && CGO_ENABLED=0 go build -o /tmp/agent ./cmd/agent
docker cp /tmp/agent dsms-dind-test:/agent
docker exec dsms-dind-test docker run -d --name agentc \
  -v /agent:/agent:ro -v /proc:/host/proc:ro -v /sys:/host/sys:ro \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e HOST_PROC=/host/proc -e HOST_SYS=/host/sys \
  -e NODE_ID=$(docker exec dsms-dind-test docker node ls --format '{{.ID}}') \
  -e PANEL_URL=http://<шлюз docker0>:9000 -e DSMS_AGENT_TOKEN=dev-token \
  busybox /agent

# 4. Панель — http://127.0.0.1:19000. Эталон для цифр:
docker exec dsms-dind-test docker stats --no-stream

# 5. Убрать за собой.
docker rm -f -v dsms-dind-test && docker image rm docker:<версия>-dind
```

Перезапуск панели в стенде: `kill $(pidof panel)` (в busybox `pkill -x` процесс
не находит — старая панель остаётся и держит порт, новая молча не стартует).
